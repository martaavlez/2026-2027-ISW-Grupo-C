# Requisitos no funcionales

Los requisitos no funcionales describen cómo debe comportarse el sistema: su calidad y sus restricciones técnicas. Siguen las categorías del Tema 3 y se expresan de forma medible, con un criterio para comprobar si se cumplen. Alimentan los contenedores del modelo C4 y los registros de decisiones de arquitectura (ADR).

> Los valores numéricos son objetivos propuestos por el equipo y pueden ajustarse durante el desarrollo.  

| ID | Categoría | Requisito | Cómo se verifica | Historias relacionadas |
| --- | --- | --- | --- | --- |
| RNF-01 | Portabilidad | El sistema será una aplicación web adaptable, compatible con las dos últimas versiones de Chrome, Firefox, Safari y Edge, que se podrá usar desde el ordenador y desde el navegador del móvil con una sola dirección web. No habrá una aplicación móvil nativa. | Recorrer los flujos principales en cada navegador indicado y en un móvil de 390 px de ancho, sin desplazamiento horizontal. | Todas |
| RNF-02 | Seguridad · control de acceso | Antes de ejecutar cualquier acción o mostrar cualquier contenido, el sistema comprobará en el servidor el rol del usuario y el nivel de privacidad del contenido. No basta con ocultar opciones en la interfaz. | Intentar acceder sin permiso a una acción o a un contenido (por ejemplo, ver un tablero privado ajeno) y comprobar que el servidor lo rechaza. | HU-04, HU-13, HU-22, HU-24, HU-29, HU-32, HU-34, HU-37, HU-39, HU-40, HU-43, HU-51, HU-55, HU-57 |
| RNF-03 | Seguridad · credenciales | Las contraseñas se guardarán cifradas con una función de resumen segura con sal (por ejemplo, bcrypt) y deberán tener al menos 8 caracteres con una letra y un número. Todas las comunicaciones usarán HTTPS. La recuperación de contraseña no revelará si un correo está registrado. | Revisar la base de datos (ninguna contraseña legible) y probar el registro con contraseñas inválidas y la recuperación con un correo no registrado. | HU-01, HU-02, HU-18 |
| RNF-04 | Seguridad · protección de datos | El tratamiento de los datos personales cumplirá el RGPD. El usuario aceptará la política de privacidad al registrarse y podrá eliminar su cuenta con todos sus datos asociados. | Comprobar que, tras eliminar una cuenta, no queda ningún dato personal de ese usuario. | HU-01, HU-19 |
| RNF-05 | Fiabilidad · disponibilidad | Si MusicBrainz no responde, la búsqueda y las fichas seguirán funcionando con el contenido ya importado y el usuario no verá ningún mensaje de error. El administrador de la plataforma verá en su panel la fecha de la última importación correcta y que la importación se reintentará cada hora. | Simular la caída de MusicBrainz y comprobar que se puede buscar y consultar fichas sin errores y que el panel del administrador muestra el aviso. | HU-03, HU-04, HU-20, HU-59 |
| RNF-06 | Fiabilidad · persistencia | Toda la información descrita en los requisitos de información se almacenará en una base de datos propia. Cada domingo se hará una copia de seguridad completa de la base de datos; se asume que, si hay un fallo, se pueden perder como mucho los datos de una semana. | Comprobar que existe la copia del último domingo y que se puede restaurar completa en un entorno de prueba. | Todas |
| RNF-07 | Fiabilidad · supervisión de la IA | Todas las acciones del agente de IA quedarán registradas con su fecha y su motivo. Cualquier cambio que no sea una corrección segura deberá validarlo el administrador de la plataforma. | Revisar que cada corrección automática aparece en el registro y que el resto genera una incidencia. | HU-21, HU-22 |
| RNF-08 | Usabilidad | Al menos el 80 % de los participantes en la prueba de usabilidad deberá completar sin ayuda las tareas principales (registrarse, buscar una canción, valorarla y añadirla a un tablero), con una satisfacción media de 4 sobre 5 o más. | Prueba de usabilidad del Sprint 1 con usuarios reales. | HU-01, HU-03, HU-05, HU-25 |
| RNF-09 | Rendimiento | Con 100 usuarios simultáneos, el 95 % de las búsquedas y de las cargas de fichas deberá responder en menos de 2 segundos. | Prueba de carga con una herramienta como JMeter o k6. | HU-03, HU-04, HU-59 |
| RNF-10 | Compatibilidad | El sistema se integrará con la API pública de MusicBrainz, respetando su límite de una petición por segundo e identificándose con el User-Agent de la aplicación, y con un servicio de correo electrónico para la recuperación de contraseña y los avisos. En las pruebas automáticas y en el pipeline se usará una versión simulada (mock) de MusicBrainz. | Probar la importación con el mock y con la API real, y el envío real de un correo de recuperación y de un aviso. | HU-11, HU-18, HU-20 |
| RNF-11 | Seguridad · sesión | Al iniciar sesión, el servidor entregará un token JWT firmado y con caducidad (24 horas). La aplicación web lo enviará en cada petición a la API, y el servidor rechazará los tokens caducados o manipulados. Al cerrar sesión, el token se elimina del navegador. | Hacer peticiones con un token caducado y con uno modificado y comprobar que el servidor las rechaza. | HU-02, HU-17 |
