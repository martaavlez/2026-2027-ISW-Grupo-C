# Requisitos no funcionales (RNF)

Los requisitos no funcionales describen cómo debe comportarse el sistema: su calidad y sus restricciones técnicas. Siguen las categorías del Tema 3 y se expresan de forma medible, con un criterio para comprobar si se cumplen. Alimentan los contenedores del modelo C4 y los registros de decisiones de arquitectura (ADR).

> Los valores numéricos son objetivos propuestos por el equipo y pueden ajustarse durante el desarrollo.

| ID | Categoría | Requisito | Cómo se verifica | Historias relacionadas |
| --- | --- | --- | --- | --- |
| RNF-01 | Portabilidad | El sistema dispondrá de una aplicación móvil para Android 10 o superior e iOS 15 o superior, y de una versión web compatible con las dos últimas versiones de Chrome, Firefox, Safari y Edge. Ambas ofrecerán las mismas funcionalidades sobre la misma información. | Recorrer los flujos principales en cada plataforma y navegador indicados. | Todas |
| RNF-02 | Seguridad · control de acceso | Antes de ejecutar cualquier acción o mostrar cualquier contenido, el sistema comprobará en el servidor el rol del usuario y el nivel de privacidad del contenido. No basta con ocultar opciones en la interfaz. | Intentar acceder sin permiso a una acción o a un contenido (por ejemplo, ver un tablero privado ajeno) y comprobar que el servidor lo rechaza. | HU-04, HU-13, HU-22, HU-24, HU-29, HU-34, HU-37, HU-39, HU-40, HU-43 |
| RNF-03 | Seguridad · credenciales | Las contraseñas se guardarán cifradas con una función de resumen segura con sal (por ejemplo, bcrypt) y deberán tener al menos 8 caracteres con una letra y un número. Todas las comunicaciones usarán HTTPS. La recuperación de contraseña no revelará si un correo está registrado. | Revisar la base de datos (ninguna contraseña legible) y probar el registro con contraseñas inválidas y la recuperación con un correo no registrado. | HU-01, HU-02, HU-18 |
| RNF-04 | Seguridad · protección de datos | El tratamiento de los datos personales cumplirá el RGPD. El usuario aceptará la política de privacidad al registrarse y podrá eliminar su cuenta con todos sus datos asociados. | Comprobar que, tras eliminar una cuenta, no queda ningún dato personal de ese usuario. | HU-01, HU-19 |
| RNF-05 | Fiabilidad · disponibilidad | Si la fuente externa del catálogo no responde, la búsqueda y las fichas seguirán funcionando con el contenido ya importado, y la importación se reintentará cada hora. | Simular la caída de la fuente externa y comprobar que se puede buscar y consultar fichas. | HU-03, HU-04, HU-20 |
| RNF-06 | Fiabilidad · persistencia | Toda la información descrita en los requisitos de información se almacenará en una base de datos propia, con una copia de seguridad diaria. | Comprobar que existe la copia del día y que se puede restaurar. | Todas |
| RNF-07 | Fiabilidad · supervisión de la IA | Todas las acciones del agente de IA quedarán registradas con su fecha y su motivo. Cualquier cambio que no sea una corrección segura deberá validarlo el administrador de la plataforma. | Revisar que cada corrección automática aparece en el registro y que el resto genera una incidencia. | HU-21, HU-22 |
| RNF-08 | Usabilidad | Al menos el 80 % de los participantes en la prueba de usabilidad deberá completar sin ayuda las tareas principales (registrarse, buscar una canción, valorarla y añadirla a un tablero), con una satisfacción media de 4 sobre 5 o más. | Prueba de usabilidad del Sprint 1 con usuarios reales. | HU-01, HU-03, HU-05, HU-25 |
| RNF-09 | Rendimiento | Con 100 usuarios simultáneos, el 95 % de las búsquedas y de las cargas de fichas deberá responder en menos de 2 segundos. | Prueba de carga con una herramienta como JMeter o k6. | HU-03, HU-04 |
| RNF-10 | Compatibilidad | El sistema se integrará con la base de datos musical externa a través de su API pública y con un servicio de correo electrónico para los envíos de recuperación de contraseña. | Probar la importación desde la API y el envío real de un correo de recuperación. | HU-18, HU-20 |
